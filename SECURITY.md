# Security model

isolmaSS keeps captures local **unless you connect your own Cloudflare installation and choose Upload**. Copy and Save never upload. When no Worker is paired, Upload opens setup and the screenshot stays in memory until you approve Cloudflare access and the Worker is installed. Upload encodes the flattened selection to a private temporary file, sends it over HTTPS to your Worker from a background thread and deletes the file when the upload card closes. The card copies or opens only a link of the exact form `<your Worker origin>/i/<32-character id>` that the Worker returned; any other response is rejected. **Redact** writes opaque dark pixels after all other annotations. Blur and highlighter preserve underlying visual information and must not be used to hide secrets. Verify the flattened PNG/JPEG before uploading sensitive material.

## Optional Cloudflare share threat model

Each installation creates a new Worker with one SQLite-backed Durable Object in the user's selected Cloudflare account; `ss.isolmaz.com` is an information/download site, not a central image host or OAuth callback server. The desktop app uses Cloudflare authorization code + PKCE and a loopback callback with random state. The authorization request explicitly includes the required `workers-scripts.write` and `memberships.read` scopes; the publisher OAuth client must also have both scopes configured as required. The user reviews them before consenting; when the token response lists the granted scopes, setup stops if a required scope was deselected. The loopback listener ignores idle or malformed local connections and accepts only a callback whose random state matches. The Cloudflare access token stays in memory during installation, is sent only to Cloudflare API hosts, and is never used for image uploads. Separate 256-bit upload and administrator Worker secrets are stored in the current Windows user's DPAPI-protected file, outside `settings.json`, and deployed as Worker secret bindings. The app may claim a new `workers.dev` account subdomain if none exists; it does not rename an existing one or modify other Workers. If the new Worker's `workers.dev` address has not answered within the setup wait, the pairing is still stored, because the Worker already exists in the user's account with keys only this computer holds. Network retries repeat only connection-stage failures and lost responses to reads, so an upload is never sent twice. When a host name cannot be resolved, the app removes only that host's entry from the Windows DNS cache before retrying. During setup, each membership account is probed with a read of its Workers subdomain; accounts the token cannot manage are not offered. Never disclose either Worker secret or publish credential files. A stolen upload secret can consume storage/quota; an administrator secret can change settings and delete images. Disconnecting this computer leaves the remote Worker intact; revoke Cloudflare OAuth consent through your Cloudflare account. **Update Worker** requests consent again, finds the Worker by the stored account and script name (or among the authorized accounts), re-uploads only the code with the same secrets and without repeating the Durable Object migration, and confirms the new version before saving.

Each public link contains an independent 192-bit random ID. There is no public listing or sequential ID space, and GET checks the private Durable Object database before streaming the stored image. A **valid link remains a bearer capability**: anyone who sees it can view an unprotected image and retain a local copy. Optional image passwords are transported over HTTPS, stored as per-image salted PBKDF2 verifiers, and never placed in URLs; repeated wrong guesses are limited. The same default password reused on many images links their access—use a strong, unique secret when privacy matters. No web service can guarantee absolute security against link disclosure, endpoint compromise or previously downloaded copies.

The API accepts PNG/JPEG with bounded streaming request size and basic image header/dimension checks, never SVG/HTML. It sends fixed image MIME, `nosniff` and CSP headers; password pages and unlocked images use `no-store`, while unprotected images are cached as immutable under their random ID, so a browser that already loaded one can keep showing its cached copy after deletion. It does not perform a full antivirus scan or decode/re-encode untrusted JPEG; grant upload credentials only to your own devices. Deleting an image removes its metadata and image chunks within the same Durable Object transaction; the alarm expires old images. A response already sent before deletion or stored by a viewer cannot be revoked. Viewing is never blocked by a quota, so nobody can lock others out of an image by refreshing it; the only quota action is stopping new uploads. Each IP address may view or unlock at most 60 times per minute (Cloudflare rate-limiting binding, approximate and per location), and public images are cacheable and revalidate with `304` without reading storage, so repeated refreshes cost little. Views are counted once per visitor, image and day using a salted, daily hash of the IP address; raw addresses are not stored and the hashes are deleted daily. A distributed attack from many addresses can still use up the account's daily Workers request allowance; on the Free plan that makes the Worker unavailable until the UTC reset rather than billing. Quotas count this Worker's traffic, not account-wide usage, and do not guarantee a zero bill. Cloudflare logs/traces and account-level access records remain under the installation owner's Cloudflare settings.


## Signed updates

The installed application checks `https://api.github.com/repos/isolmaz/isolmaSS-app/releases/latest` (0.6.0 and older checked a release repository that is no longer public, so they cannot update themselves; install a current version manually). It accepts only a newer, non-draft, non-prerelease numeric three-part version with one `isolmass-setup.exe` and one `isolmass-setup.exe.sig`. Download URLs require HTTPS and an allowed GitHub asset host. Redirects remain HTTPS and bounded; metadata and installer downloads have size limits.

GitHub's SHA-256 asset digest is compared with the downloaded executable. The detached 384-byte RSA-3072/PKCS#1 v1.5 SHA-256 signature authenticates the exact UTF-8 message `isolmaSS-update-v1\n<VERSION>\n<SHA256-LOWERCASE-HEX>\n`. Windows BCrypt verifies it against the embedded publisher public key. The pinned key is `resources/update-public-key.blob` (SHA-256 `67906f6348c629e2c34c1cd849b742249bc32ebc104275a990bae5a7ddc2f20e`). The executable's file version must equal the signed release version. Immediately before launching a staged installer, the app checks its canonical staging path, digest, detached signature and file version again.

The publisher's private key is **non-exportable** in the release workstation's `Cert:\CurrentUser\My` Windows certificate store. It is never stored in this repository, on any build service or in GitHub releases. `scripts/sign-update.ps1` refuses any certificate whose public key differs from the pinned key. If that workstation/key is lost, future releases cannot be installed automatically by apps pinned to this key; recovery requires a new manually installed trust root. Keep the signing account and workstation protected.

The signature is application-level and does **not** establish Authenticode trust in Windows. SmartScreen may warn on a downloaded installer or portable executable. Do not disable SmartScreen or automatically dismiss its warning.

## Consent and rollback

Checking for updates never authorizes installation. The native prompt offers **Install / Later / Skip this version**. A version skipped during automatic checks remains available through a manual check. Download and installer launch happen only after explicit installation consent. The consent prompt warns that the app will close for installation and start again; manual checks expose progress and results in Settings or the tray. The app waits for active editing, settings and synchronous copy/save work to finish before handing control to the installer.

The installer stages the new executable beside the installation, retains the rollback executable, waits for the old process, and runs `--health-check` against the installed new executable. That check exercises settings, tray and shortcut startup. The installer confirms the restarted tray is present before deleting the rollback executable. On failure it attempts to restore the executable and display version and surfaces an error. If a process or permission prevents restoration, it leaves the backup on disk and reports its path. The rollback protects executable activation; it is not a backup of screenshots or personal configuration.

## Input, persistence and diagnostics

Configuration is validated when read: path length, color alpha, 1–64 px width, supported shortcut, save format/quality, delay, last tool and skipped release version. Missing fields receive defaults. The settings file is bounded to 64 KiB and saved using a cross-process lock, staged file and atomic rename; malformed content is backed up before defaults are used. Save output uses temporary files and atomic replacement where supported. Resource handles and clipboard ownership are released on failure paths.

Diagnostic logs are local, rotate near 1 MiB, and omit screenshots, annotations, recorded keys and downloaded private credentials. File paths and operating-system error text may be present; review logs before sharing. Never commit Worker secrets, local DPAPI files or the signing private key.

For a suspected vulnerability, report it privately through GitHub's private vulnerability reporting (**Security › Report a vulnerability** in this repository) or by email to **info@isolmaz.com**; do not put secrets or private captures in a public issue.
