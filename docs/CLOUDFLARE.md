# Cloudflare sharing

There is **no central isolmaSS image host or sign-in**. Sharing uses a Worker that the app installs in your own Cloudflare account; Copy and Save never upload.

**Setup (first Upload).** The editor steps aside, keeping the capture in memory, and the connection window opens with its own taskbar button. Choose **Continue with Cloudflare**, sign in in the browser and approve the two requested permissions, `workers-scripts.write` and `memberships.read`, for the account you want. Sign-in may take up to 10 minutes. The window comes back to the front; accounts you did not authorize for Workers are hidden, and with a single account installation starts immediately. The app creates a randomly named Worker with a private SQLite Durable Object, enables its `workers.dev` address, protects the generated Worker keys with Windows DPAPI and uploads the pending screenshot. A brand-new `workers.dev` address can take a few minutes to resolve; the pairing is kept meanwhile and uploads work once it answers. No GitHub account, key pasting, R2, D1 or custom domain is needed. The OAuth access token is used only during installation and never stored.

**Cloudflare window.** Once paired it has three tabs and loads current data when opened:

- **Connection** — Worker address, today's and this month's uploads and views, stored images and size, an optional password for new uploads, **Refresh**, **Disconnect** (removes the connection from this computer only; the Worker and images stay) and, when the Worker runs older code than the app bundles, **Update Worker**. Updating asks for Cloudflare consent once more and replaces only the Worker's code; its address, links, keys, images and settings stay. On the consent page allow the account that owns the Worker: the app finds it by the Worker address's workers.dev subdomain, and names the address and the allowed accounts if it is not among them.
- **Limits** — images kept (50), daily uploads (20), a daily view level for warnings (1,000), size per image (10 MB) and in total (800 MB), retention (30 days) and the warning threshold (90%). At the threshold choose *warn* or *stop new uploads*. Viewing is never blocked by a quota. Counters cover this Worker only, use UTC days, and **no setting guarantees a zero invoice**.
- **Images** — recent images with local time, size, views and password status; **Open** (or double-click), **Copy link** and **Delete**. Deleted and expired links stop working immediately for new viewers; copies already downloaded, including a viewer's browser cache, cannot be revoked.

A valid link without a password can be viewed by anyone who has it. With a password, only a salted per-image verifier is stored; share the password separately.

## Troubleshooting

**If something goes wrong,** dialogs and the upload card show Cloudflare's own error code and message.

- *Could not check the Cloudflare Workers subdomain (403)*: the chosen account does not grant you Workers access, or the publisher's OAuth client is private (usable only by members of its own account). Pick another account.
- *Your computer could not resolve …*: Windows could not resolve the Worker's host name. The app clears that DNS cache entry and retries automatically; if it persists, check the adapter's DNS servers, especially IPv6 servers on a network without IPv6.
- *401*: the Worker's keys do not match this computer; connect again. The existing Worker is left untouched.
- *429 on upload / 507*: the daily upload limit or the storage limit is reached; wait for the UTC reset, raise the limit or delete images.
- *429 on upload* also carries `Retry-After`, the seconds until the next UTC midnight, when the daily upload count is the cause.
- *"Too many requests" page when viewing*: one address opened links more than 60 times in a minute; it can view again a minute later.
- *"Too many attempts" page on a password-protected link*: 20 wrong passwords were entered for that link within the hour; the link unlocks again when the hour ends.

## Worker API

`cloudflare/worker.mjs` is the per-user Worker; `cloudflare/wrangler.jsonc` binds `STORE` to its SQLite `ShareStore` Durable Object. `cloudflare/.dev.vars.example` is a local template; never commit real secrets.

- `POST /api/upload` requires the `UPLOAD_TOKEN` bearer secret and PNG/JPEG bytes; optional `X-Image-Password` carries a padding-free base64url UTF-8 password (12–128 printable characters). Success: `201 {"id":"<192-bit id>","url":"https://<worker>/i/<id>"}`. An image over the size limit is refused with `413`, and when today's upload limit is already reached the Worker answers `429` before reading the image.
- `POST /api/setup`, `GET/PUT /api/settings`, `GET /api/stats`, `GET /api/images?limit=50&offset=0` and `DELETE /api/images/:id` require the separate `ADMIN_TOKEN` bearer secret.
- `GET` and `HEAD /i/:id` answer a browser navigation (`Sec-Fetch-Dest: document`, or `Accept: text/html` when `Sec-Fetch-Dest` is absent) with a viewer page: the screenshot, **Download** with a dated file name, **Open original** and Open Graph and Twitter card tags that point at the raw image. Every other request, such as an `<img>` embed or a chat unfurler, receives the image bytes. `/i/:id.png` and `/i/:id.jpg` always return the bytes (the extension must match the stored format). A password-protected link answers with the password form instead, and with the bytes once the visitor holds the unlock cookie.
- `POST /i/:id/unlock` checks the password, with at most 20 wrong attempts per link and hour (the count is reserved before the password is checked, so simultaneous guesses cannot exceed it). A wrong password shows the form again with `403` and an inline error; a correct one answers `303` back to `/i/:id` and sets a signed cookie (`HttpOnly; Secure; SameSite=Lax`, scoped to that link, valid for one hour), so reloading, opening in a new tab and saving the image all work. The signing key is generated per Worker and stored in its database.
- Every page a viewer can see is HTML in Turkish when the browser's first preferred language is Turkish and in English otherwise, with the Windows 11 look and light and dark themes; there is no script. Unknown, expired or deleted links show a "no longer available" page (`404`), too many wrong passwords `429` and too many requests `429`, both with `Retry-After`. JSON errors are only returned under `/api/`. `HEAD` returns the headers of the matching `GET` (including `Content-Length`) without a body and without counting a view; other methods get `405` with `Allow`.
- Viewing and unlocking are rate-limited to 60 requests per minute per IP address through Cloudflare's rate-limiting binding; if an account refuses that binding the Worker runs without it. `/favicon.ico`, `/favicon.svg`, `/robots.txt` (a `404`; it deliberately does not disallow `/i/`, so crawlers see the noindex header) and `/` (a noindex page) are answered at the edge, before the limiter and without waking the Durable Object, and any other path outside `/i/` and `/api/` is a cheap `404`.
- Images without a password are immutable under their ID, but only until they expire: responses carry `Cache-Control: private, max-age=<seconds until expiry>, immutable`, an `ETag` and `Vary: Accept, Sec-Fetch-Dest`, so a browser may reuse them and a shared cache may not keep them. A revalidation reaches the Durable Object, which answers `304` only for an image that still exists. Password pages, viewer pages and error pages use `no-store`; unlocked images use `private, no-store` with `Vary: Cookie`. Image responses are sent with a known `Content-Length`. Everything under `/i/` carries `X-Robots-Tag: noindex, nofollow, noimageindex`. API and error JSON responses carry `Content-Security-Policy: default-src 'none'; frame-ancestors 'none'`, `nosniff` and `no-referrer`; HTML pages carry a CSP that allows only inline styles and same-origin or `data:` images; image bytes carry `default-src 'none'; sandbox`.
- A view counts once per visitor, image and UTC day, whether the visitor opens the viewer page or the image; `HEAD` requests and `304` revalidations are not views. The visitor is a salted, day-specific hash of the IP address; raw addresses are never stored and the hashes are deleted when the day ends.
- `POST /api/setup` and `GET /api/stats` report the Worker version; the app offers **Update Worker** when it bundles newer code. Version 4 introduced the viewer page, the HTML error pages, the unlock redirect and `/i/:id.png`, so a Worker installed by an earlier app version is offered that update. Updating keeps the address, links, keys, images and settings; the Worker adds the new columns and key to its database on its own.

**Local testing.** Copy `.dev.vars.example` to `.dev.vars` and fill both tokens with 43-character base64url values, for example from `python -c "import secrets; print(secrets.token_urlsafe(32))"`; other formats are rejected with `401`. Then run `npx wrangler@4 dev` in `cloudflare/`. With wrangler 4 the local rate-limiting binding made `/i/*` requests fail with `500`; test with a copy of `wrangler.jsonc` without `ratelimits`.

**Automated tests.** In `cloudflare/`, run `pnpm install` once, then `pnpm test` (Vitest inside workerd, with the real SQLite Durable Object and test secrets from `vitest.config.mjs`) or `pnpm coverage` (Istanbul, thresholds of 100 % on `worker.mjs`). The tests call the Worker's handler directly and leave the rate-limiting binding out unless a test supplies one.

Images are stored in chunks of at most 1 MB. Consult Cloudflare's [Workers limits](https://developers.cloudflare.com/workers/platform/limits/) and [Durable Objects limits](https://developers.cloudflare.com/durable-objects/platform/limits/); free allowances are shared by the whole account.
